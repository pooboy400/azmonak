تصمیم‌های قابل وتو

مثل D13 تا D16 در سند توسعه، پیش‌فرض‌های زیر با منطق مهندسی گذاشته شده‌اند و رأی صریح پویا هر زمان بیاید جایگزین می‌شود. هیچ‌کدام با قیدهای سخت فصل ۱ ناسازگار نیستند؛ وتوی هر ردیف فقط طراحی همان بخش را عوض می‌کند نه ساختار کل.

فصل ۱۲
نقشه راه پیاده‌سازی فرانت

ترتیب پیشنهادی ساخت، از پوسته به پیچیدگی: اول شالوده‌ای که همه‌ی صفحات روی آن می‌نشینند، بعد صفحات با کمترین وابستگی به API گام ۲، و در انتها داشبورد داده‌محور. هر گام یک معیار پذیرش روشن دارد تا جلوتر «تمام‌شدن» قابل بحث نباشد.

  1. گام F1 — پوسته و توکن‌ها: layout سراسری RTL، متغیرهای CSS فصل ۲، وزیرمتن سابست، هدر و ناوبری موبایل فصل ۴. پذیرش: همه‌ی صفحات خالی با پوسته‌ی صحیح رندر می‌شوند و Lighthouse پوسته بالای ۹۰ است.
  2. گام F2 — لندینگ: قیف سه‌قدمی فصل ۵ با فوتر کامل. پذیرش: لندینگ ریسپانسیو از ۳۶۰ تا ۱۲۸۰ پیکسل و بدون تصویر سنگین.
  3. گام F3 — ورود: جریان OTP با استیت‌منیج کلاینت و حالت‌های خطا. پذیرش: تا API گام ۲، ورود آزمایشی با کد دلخواه کار می‌کند و لاگین در localStorage می‌ماند.
  4. گام F4 — پروفایل (نسخه داده‌ی نمونه): داشبورد فصل ۸ با داده‌های ساختگی هم‌ساخت خروجی core. پذیرش: نمودار دولایه SVG و چیپ‌های سطح از داده واقعی‌نما رندر می‌شوند.
  5. گام F5 — فرم آزمون: حالت فوکوس کامل با مرحله‌ی اعتماد D14، بازخورد و خلاصه‌ی پایان. پذیرش: جلسه‌ی ۱۰ سؤالی با داده‌ی نمونه از اول تا آخر بدون خطا می‌رود — تمرین نهایی تست دود تسک 3.8.
  6. گام F6 — لیدربرد و کامیونیتی: پودیوم، لیگ‌ها، فید کارت‌ها با داده‌ی نمونه. پذیرش: سوییچ‌های حریم خصوصی در UI فعال و تب‌ها با داده‌ی خالی/پر هر دو درست رندر می‌شوند.
  7. گام F7 — اتصال به API گام ۲: جایگزینی داده‌ی نمونه با خروجی واقعی core از طریق بک‌اند. پذیرش: جریان کامل ورود تا خلاصه‌ی جلسه روی API واقعی سبز شود و بودجه ۲۰۰KB پاس شود.
یادآوری معماری
فرانت هیچ منطق الگوریتمی‌ای در خود ندارد — طبق قاعده‌ی شماره ۲ سند توسعه، بک‌اند فقط core را صدا می‌زند و فرانت فقط از API می‌خواند. همین تفکیک است که ادعای «الگوریتم جدا از رابط» سند را در دفاع جشنواره قابل اثبات می‌کند و اجازه می‌دهد هر صفحه‌ی این سند بدون دست‌زدن به موتور، مستقل بهبود یابد.
